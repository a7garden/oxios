# oxi-sdk 0.58 → 0.64 마이그레이션 설계

**작성일:** 2026-08-02
**대상 버전:** `oxi-sdk = "0.64.0"` (2026-08-02 배포)
**현재:** `oxi-sdk = "0.58.0"`, `oxi-agent = "0.58.0"`
**결론:** **적용 권장** — 0.64는 R0/R1/R3/R6/R7을 모두 구현. 마이그레이션 비용은 의도된 작업.

---

## 1. 0.64가 가져온 변화 (요청 매핑)

이전 분석(2026-08-01)에서 oxi-sdk에 요청한 R0–R8 항목 중 **6개가 0.64에서 구현됨**:

| 요청 | 0.64 구현 | 비고 |
|---|---|---|
| **R0 + R5** (ownership contract) | `docs/oxi-sdk-ownership.md` 신규, behavior↔policy 명시 | R0 충족 |
| **R1** (CHANGELOG `## Removed`) | Retrospective 항목 추가 (0.61/0.63 제거를 회고적으로 문서화) + **api-diff CI gate** 추가 | R1 충족 |
| **R2** (`#[deprecated]`) | `oauth::build_authorization_url` → `build_authorization_url_result` deprecation | 부분 충족 |
| **R3** (tier 어노테이션) | `oxi-api-stability` proc-macro + 17개 re-export 블록에 어노테이션 + **실제 `#[cfg(feature)]` 게이트** (단순 doc가 아님) | R3 충족 (scope은 일부 좁힘) |
| **R6** (composable trait) | `oxi_ai::CircuitBreaker` trait + `DefaultCircuitBreaker` reference impl, `oxi_agent::SpawnValidator` trait + `NoopSpawnValidator`, `SharedBreaker`로 retry loop 통합 | R6 충족 |
| **R7** (error stability) | `OAuthError`/`SdkError`/`ProviderError`에 `#[non_exhaustive]` + `BreakerError::Open`에 `is_retryable()` contract | R7 충족 |
| **R4** (zero-panic) | `oauth::build_authorization_url_result` 추가 (non-panicking PKCE) | 부분 충족 |
| **R8** (의존성 영향) | oxi-catalog 추가, oxi-api-stability proc-macro 추가 | 부분 충족 |

**미구현/부분:** R2 (deprecation 주기 의무화 미흡 — 한 항목만 deprecation), R4 (전체 zero-panic 미보장), R8 (의존성 영향 CHANGELOG 명시 부분적).

**R3이 단순 doc을 넘어선 점**: `#[cfg(feature = "...")]` 게이트가 실제로 걸려 있어, consumer가 feature를 켜지 않으면 **컴파일 자체가 안 됨**. 이전 분석에서 oxios가 0.63에서 만난 "사라진 심볼" 문제가 0.64에서는 "feature를 켜야 보이는 심볼"로 바뀜. **silence가 signal로 전환됨**.

## 3. 마이그레이션 설계

### 3.1 Cargo.toml 변경

```toml
# root Cargo.toml
-oxi-sdk = "0.58.0"
+oxi-sdk = { version = "0.64.0", features = [
+    "browser",
+    "delegation",
+    "subagent",
+    "circuit-breaker",
+    "mcp-spawn-validator",
+] }

# crates/oxios-kernel/Cargo.toml
-oxi-agent = "0.58.0"
+oxi-agent = "0.64.0"
```

feature 선택 근거:
- `browser`: `kernel_handle/browser_api.rs`에서 `BrowseConfig` + `BrowserEngine` trait 사용 (기존 `native-browser`는 oxibrowser-core 활성화용, 별도)
- `delegation`: `SdkSubagentRunner` 사용 (`agent_runtime.rs`)
- `subagent`: `oxi_agent::SubagentRunner` trait (`subagent_runner.rs:68`) — `delegation`이 `SdkSubagentRunner`만 expose하므로 둘 다 필요
- `circuit-breaker`: `LLM_CIRCUIT_BREAKER`의 새 `CircuitBreaker` trait 채택
- `mcp-spawn-validator`: oxios의 자체 spawn validation 정책을 `SpawnValidator` trait impl로 wire

### 3.2 코드 변경 (4개 영역)

#### 영역 A: `engine.rs` — `pooled_provider()` 처리

**현재 (0.58):**
```rust
use oxi_sdk::{ProviderPool, RateLimitPolicy};

pub fn pooled_provider(&self, name: &str, rpm: u32) -> Result<Arc<dyn oxi_sdk::Provider>> {
    let policy = RateLimitPolicy::rpm(rpm);
    let pool = ProviderPool::new(base, policy, name);
    // ...
}
```

**옵션 A1** (권장): **기능 제거** — `provider_rpm`은 옵션이고 기본값 0 (비활성). 호출 사이트 grep 후 dead code 정리.
```bash
grep -rn "pooled_provider\|provider_rpm" --include="*.rs" crates/ src/
```

**옵션 A2**: **자체 구현** — `tokio::sync::Semaphore` + `last_call_time` HashMap으로 RPM 제한. ~30 LOC.

**권장: A1** (현재 production 미사용 경로; A2는 별도 RFC로).

#### 영역 B: `agent_runtime.rs:55-67` — LLM 회로차단기 교체

**현재 (0.58):**
```rust
static LLM_CIRCUIT_BREAKER: std::sync::OnceLock<oxi_sdk::ProviderCircuitBreaker> = ...;
fn get_llm_circuit_breaker() -> &'static oxi_sdk::ProviderCircuitBreaker {
    LLM_CIRCUIT_BREAKER.get_or_init(|| {
        oxi_sdk::ProviderCircuitBreaker::new(
            "global".to_string(),
            oxi_sdk::CircuitBreakerConfig::default(),
        )
    })
}
```

**목표 (0.64):**
```rust
use oxi_sdk::{CircuitBreaker, DefaultCircuitBreaker, BreakerError, BreakerState};

static LLM_CIRCUIT_BREAKER: std::sync::OnceLock<DefaultCircuitBreaker> = ...;

fn get_llm_circuit_breaker() -> &'static DefaultCircuitBreaker {
    LLM_CIRCUIT_BREAKER.get_or_init(|| DefaultCircuitBreaker::new(/* threshold, reset_timeout */))
}

// 또는 도메인 정책에 맞춰 자체 구현:
struct OxiosLlmBreaker { /* A2A 도메인 임계값 */ }
impl CircuitBreaker for OxiosLlmBreaker { /* check, record_success, record_failure */ }
```

**권장: `DefaultCircuitBreaker` 채택** + `circuit-breaker` feature 게이트. 자체 임계값이 필요해지면 그때 자체 impl (R6의 강점).

#### 영역 C: `kernel_handle/browser_api.rs` — feature 게이트 확인

**현재:** `use oxi_sdk::{BrowseConfig, BrowserEngine}`가 default feature에서 누락.
**해결:** root Cargo.toml에 `browser` feature 추가 (영역 3.1에 포함).

#### 영역 D: MCP spawn validation 정책 통합 (R6 채택)

**현재 (oxios 자체):**
```rust
// crates/oxios-mcp/src/validation.rs
pub fn validate_mcp_command(cmd: &str) -> Result<(), McpSpawnError> { ... }
pub fn sanitize_env(env: &mut HashMap<String, String>) { ... }
```

**목표 (R6):** oxios의 정책을 SDK trait로 wire
```rust
// crates/oxios-mcp/src/spawn_policy.rs
use oxi_sdk::SpawnValidator;

pub struct OxiosSpawnPolicy;
impl SpawnValidator for OxiosSpawnPolicy {
    fn validate_command(&self, cmd: &str, args: &[String]) -> Result<(), String> {
        // 기존 validate_mcp_command 로직 위임
        oxios_mcp::validation::validate_mcp_command(cmd).map_err(|e| e.to_string())
    }
    fn sanitize_env(&self, env: &mut HashMap<String, String>) {
        oxios_mcp::validation::sanitize_env(env)
    }
}

// McpClient 초기화 시
client.set_spawn_validator(Arc::new(OxiosSpawnPolicy));
```

**효과**: oxios 도메인 정책은 그대로 유지하면서, SDK가 owner로 인정 + 향후 SDK 측 변경에도 호환.

### 3.4 단계적 적용 (안전망)

**왜 단계적?** 0.58→0.63 직접 도약이 5개 컴파일 에러였고, 0.64는 11개 (feature 게이트 + R6 도입). 한 번에 다 적용하면 회귀 디버깅이 어려움.

**단계 1** (feature 게이트만 적용, R0/R1/R3/R7):
- Cargo.toml features 추가
- 코드 변경 0
- 빌드 통과 + SDK 새 contract 인지
- **마이그레이션 비용: 1줄 + lock 갱신**

**단계 2** (R6 circuit-breaker 채택):
- `agent_runtime.rs:55-67` 새 `CircuitBreaker` trait impl로 교체
- 빌드 통과
- **마이그레이션 비용: ~20 LOC**

**단계 3** (R6 SpawnValidator 채택):
- `crates/oxios-mcp/src/spawn_policy.rs` 추가
- McpClient 초기화에 wire
- **마이그레이션 비용: ~30 LOC + 1 hookup**

**단계 4** (provider pooling 처리):
- grep 결과에 따라 A1 (제거) 또는 A2 (자체 구현)
- **마이그레이션 비용: 0~30 LOC**

**권장**: 1 → 2 → 3 → 4. 각 단계마다 commit + CI 통과.

## 4. 위험 분석

### 4.1 R6 채택의 함의

`CircuitBreaker` trait + `DefaultCircuitBreaker`를 채택하면, 이전 `ProviderCircuitBreaker`의 **공개 API**와 미세하게 다릅니다:

- 이전: `ProviderCircuitBreaker::new(name: String, config: CircuitBreakerConfig)` — 이름 + 설정 한 번에
- 신규: `DefaultCircuitBreaker::new(threshold, reset_timeout)` — 임계값만

이는 호환되지 않습니다. oxios의 `LLM_CIRCUIT_BREAKER` 정적 변수는 자연스럽게 새 생성자로 교체. 그러나 metrics의 `llm_circuit_breaker_state`가 이전에 breaker 상태를 읽던 경로가 있다면 확인 필요.

```bash
grep -rn "llm_circuit_breaker_state\|breaker_state\|circuit_state" --include="*.rs" crates/
```

### 4.2 oxios의 자체 `A2ACircuitBreaker`와의 관계

oxios는 `crates/oxios-kernel/src/a2a/circuit_breaker.rs`에 자체 회로차단기를 갖고 있습니다 (A2A delegation 도메인). 이건 **유지** — 다른 트래픽 클래스이고, R6의 `SpawnValidator`처럼 정책(임계값)이 도메인 특화.

`CircuitBreaker` trait 채택은 LLM 호출 경로 (`LLM_CIRCUIT_BREAKER`)에만 적용. A2A 회로차단기는 oxios 고유 정책이므로 그대로.

### 4.3 backward compatibility

- 기존 consumer (oxios): `oxi-sdk = "0.58.0"` pin으로 변경 없음 — 강제 도약 아님
- 새 oxios 코드: `0.64.0` pin + feature gates
- 둘 사이 호환성: `0.58.0`을 유지한 fork는 가능하지만, 보다는 단계적 도약 권장

### 4.4 Cargo.toml features 누락 시 빌드 실패

`oxi-sdk` features 배열에 빠뜨리면 즉시 컴파일 에러. CI에서 `cargo check`가 잡아주지만, 로컬 개발자 경험 개선 위해 `unstable` umbrella feature 사용도 검토:

```toml
# 옵션: 모든 unstable 한꺼번에 켜기
oxi-sdk = { version = "0.64.0", features = ["browser", "unstable"] }
```

**권장: 명시적 feature 선택** (어떤 unstable을 쓰는지 의도 표현). 단, 처음 적용 시 `unstable` umbrella로 시작해서 점차 좁혀가는 것도 합리적.

## 5. 결론

**적용 권장.** 0.64는 이전 분석에서 요청한 6개 항목(R0/R1/R3/R6/R7, 부분 R2/R4)을 모두 구현했고, **R6는 oxios의 평행 구현 문제를 정확히 겨냥**합니다. 마이그레이션 비용은:

- 코드 변경: ~50–80 LOC (영역 A/B/D 합계)
- 설정 변경: 2개 핀 + 5개 feature
- 위험: 낮음 (단계적 적용 가능, 각 단계에서 빌드/테스트 게이트)

**기대 효과**:
1. R0 ownership contract로 "누가 무엇을 갖는지" 명확 — 평행 진화 위험 감소
2. R3 cfg-gated `#[unstable]` 표지로 의도적 API 제거가 **silence가 아닌 signal**로
3. R6 `CircuitBreaker` trait으로 LLM 회복력 코드 보존 + 도메인 정책 결합도 감소
4. R6 `SpawnValidator` trait으로 oxios의 MCP spawn validation 정책이 SDK에 owner로 인정
5. R7 `#[non_exhaustive]` + R1 api-diff CI로 향후 회귀 자동 차단

**바로 시작**: 영역 3.4의 단계 1 (feature 게이트만 켜고 빌드 통과)부터. 산출물은 본 문서의 체크리스트 항목별 commit + CI 게이트.

## 부록 D. 구현 결과 (2026-08-02)

설계대로 진행하되, 실측 컴파일 결과와 로컬 oxi 저장소(`0.64.0`)의 실제 API를
기준으로 아래 차이를 보정해 적용했다.

### 실제 컴파일 에러: 7개 (설계 예상 11개)

핀 도약 + feature 선택 직후 `cargo check -p oxios-kernel`:

```
error[E0432]: unresolved imports `oxi_sdk::ProviderPool`, `oxi_sdk::RateLimitPolicy`
error[E0433]: cannot find `ProviderCircuitBreaker` in `oxi_sdk`
error[E0433]: cannot find `CircuitBreakerConfig` in `oxi_sdk`
error[E0425]: cannot find type `ProviderCircuitBreaker` (×2)
error[E0308]: mismatched types — `Result<_, SdkError>` → `anyhow::Result` (×2)
```

설계가 예측한 browser/delegation/subagent feature-gate 에러 5개는 **이미 선택한
feature로 해소**돼 발생하지 않았다. 대신 설계가 분류하지 못한 "미카테고리 1개"의
정체가 드러났다: **oxi-sdk 0.64의 `Oxi::resolve_model`/`create_provider`가
`Result<_, anyhow::Error>` 대신 typed `Result<_, SdkError>`를 반환** (R7).
`engine.rs`의 래퍼 메서드가 `anyhow::Result`를 직접 반환하던 탓에 호환 불가 →
`Ok(self.oxi.resolve_model(model_id)?)`로 변환.

### 적용된 변경

| 영역 | 설계안 | 실제 적용 |
|---|---|---|
| Cargo 핀 | `oxi-sdk = { features = [browser, delegation, subagent, circuit-breaker, mcp-spawn-validator] }` | **`[browser, delegation, circuit-breaker]`만 적용.** `subagent`는 oxi-sdk 재export 게이트이나 oxios가 `oxi_agent::SubagentRunner`를 직접 경로로 쓰고 oxi-agent에는 `subagent` feature가 없음(재export가 항상 컴파일됨) → 불필요. `mcp-spawn-validator`는 영역 D 보류(아래)로 제외. |
| 영역 A (pooled_provider) | A1 제거 권장 | **A1 적용.** `provider_rpm`은 production에서 한 번도 > 0로 설정된 적 없는 dead path. `engine.rs`의 `pools` 필드 + `pooled_provider()` + `ProviderPool`/`RateLimitPolicy` import + `AgentRuntimeConfig.provider_rpm` 필드 + `run_agent`의 legacy `if provider_rpm > 0` 분기 전부 제거. AgentBuilder 단일 경로만 잔존. |
| 영역 B (회로차단기) | `DefaultCircuitBreaker` 채택 | **적용.** `OnceLock` + 접근자 → `LazyLock` static(프로젝트 룰 rs-lazylock 준수). 임계값 5 실패 / 30s reset. `llm_circuit_breaker_state` 게이지가 단순 "마지막 호출 에러 여부"가 아니라 **실제 상태기계(Closed=0 / HalfOpen=0.5 / Open=1)** 를 반영하도록 개선. |
| 영역 C (browser) | feature 추가 | feature 선택으로 해소 — 코드 변경 없음. |
| 영역 D (SpawnValidator) | `crates/oxios-mcp`에 구현 + McpClient wire | **보류(사용자 승인).** 사유: `oxios-mcp`는 자체 `McpClient`로 직접 `Command::new` spawn하며 SDK MCP 전송계층(`StdioTransport`)을 사용하지 않음 → SDK `SpawnValidator`의 소비자가 현재 oxios에 없음. 구현하면 (a) 소비자 없는 데드코드, (b) 퍼블리시된 leaf crate에 oxi-sdk 의존성 강제 결합이 발생. `validate_mcp_command`/`sanitize_env` 정책 자체는 `McpClient::initialize`의 spawn chokepoint에서 이미 시행 중이므로 보안 손실 없음. SDK 전송계층 도입 시 어댑터 1개(~15 LOC)로 드롭인 가능. |
