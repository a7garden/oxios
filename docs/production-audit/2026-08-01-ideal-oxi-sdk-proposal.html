0. 테제: 거버넌스 + 소유 경계가 함께 가야 한다

이 문서의 균형점

이번 세션에서 oxios는 두 종류의 고통을 동시에 겪었습니다. 하나는 거버넌스(7개 root 심볼이 CHANGELOG 0건으로 사라짐, #[deprecated] 0건)이고, 다른 하나는 소유 경계의 부재(oxios가 MCP·메모리·회로차단기를 자체 구현했는데 oxi-sdk에도 동등 기능이 있어서, 어느 쪽이 진짜 owner인지 모호했고 결국 양쪽이 평행으로 진화함).

두 축을 분리해서 보면 해결책이 보이지 않습니다. 거버넌스만 강화하면 consumer는 안정적 API 위에 잘못된 추상화를 올리는 위험을 막지 못하고, ownership만 명확히 하면 그 owner가 다시 변할 때 같은 파괴가 일어납니다. 두 축을 함께 가져가야 — ownership을 명확히 한 다음, 그 ownership 경계선 위에 stability tier 어노테이션과 deprecation 규약을 얹어야 — P0.2 사태가 재발하지 않습니다.

거버넌스 50%
소유 경계 50%

요청 R0(소유 계약)이 P0. ownership을 못 박으면 R1·R2·R3(거버넌스)은 무의미.

1. 근본 원인: P0.2 사태는 거버넌스 + 소유 불명의 합작품

이번에 부러진 4개 심볼(ProviderPool, RateLimitPolicy, ProviderCircuitBreaker, CircuitBreakerConfig)의 삭제는 두 구조적 결함의 동시 발생 때문에 일어났습니다.

1.1 결함 A — 소유 경계 불명 (ownership 불명)

oxios는 자체적으로 다음을 구현했습니다. 각 항목은 oxios 도메인 정책 때문에 oxi-sdk가 제공한 동등 기능을 의도적으로 우회한 결과입니다.

기능oxios 자체 구현oxi-sdk 동등분리 사유 (실측)
MCP 클라이언트 crates/oxios-mcp/src/{client,protocol,validation}.rs oxi_agent::mcp spawn validation chokepoint: validate_mcp_command(FORBIDDEN 메타문자·..·BLOCKED_MCP_SHELLS 차단), sanitize_env(LD_PRELOAD/LD_LIBRARY_PATH/DYLD_*/PYTHONPATH 제거) — oxios의 audit remediation 설계(docs/designs/2026-07-12-audit-remediation-design.md:18-23)에서 정의된 도메인 정책.
메모리 백엔드 crates/oxios-memory/src/memory/backend.rs (MemoryBackend trait) oxi_agent::tools::MemoryBackend 3-tier 정책: Hot/Warm/Cold + Dream consolidation + HNSW + hyperbolic embedding. 2026-07-11 설계(docs/designs/2026-07-11-memory-system-overhaul-design.md:95)에서 oxi의 MemoryStore로 브릿징하는 안을 의도적으로 reject.
회로차단기 crates/oxios-kernel/src/a2a/circuit_breaker.rs (A2ACircuitBreaker) oxi_ai::circuit_breaker::ProviderCircuitBreaker (제거됨) A2A delegation 도메인: 임계값 (3 failures / 30s reset), HalfOpen 상태 머신, A2A 메시지 라우터에 직접 wire. LLM 호출 회로차단기와는 다른 트래픽 클래스.

여기서 핵심 문제는: oxios가 자체 구현한 이유는 합리적이지만, 그 사실이 oxi-sdk에는 전달되지 않았다. oxi-sdk 입장에서 자기 ProviderCircuitBreaker는 oxios가 쓸 줄 모르는 자체 기능이고, oxios 입장에서 자기 A2ACircuitBreaker는 도메인 정책의 표현이다. 두 owner가 자기 영역을 모르고 있다가, 어느 쪽이 망가질 때 양쪽이 같이 무너집니다.

1.2 결함 B — 거버넌스 부재 (silence on removal)

동일한 사실이 다른 각도에서 보입니다:

  • 7개 root-level 심볼 (ProviderPool, RateLimitPolicy, CircuitBreakerConfig, ProviderCircuitBreaker, MultiProviderBuilder, RoutingConfig, MultiProviderConfig)이 0.61에서 사라짐.
  • CHANGELOG 0.56–0.63 (166개 섹션) 중 ## Removed 또는 ## Breaking로 분류된 항목 0건.
  • CHANGELOG에서 ProviderPool/ProviderCircuitBreaker/RateLimitPolicy/CircuitBreakerConfig 언급 1회 (제거 기재 아님).
  • 0.63의 oxi-sdk/src에서 #[deprecated] 어노테이션 0건.
  • Stability tier 어노테이션 (#[stable] / #[unstable] / #[internal]) 0건.

1.3 두 결함의 합작: P0.2의 작동 메커니즘

단계 1 — oxi-sdk: ProviderCircuitBreaker를 opt-in 표지(커밋 메시지에만 존재)로 도입.
단계 2 — oxios: 표지가 기계 판독 불가라 opt-in임을 모르고, 핵심 회복력 위에 사용. 같은 시점에 자체 A2ACircuitBreaker도 만듦 (다른 트래픽 클래스).
단계 3 — oxi-sdk: P0.2b 리팩터링에서 "프로덕션 미사용" 판단(ae441c1f: "never constructed in production")으로 회로차단기 삭제. deprecation 경고 없이, CHANGELOG 기록 없이.
단계 4 — oxios: 빌드 깨짐. 자체 A2ACircuitBreaker는 oxios 도메인 정책의 표현이라 그대로지만, LLM 경로의 회복력 보강 코드는 죽음.

두 결함 중 하나만 있었어도 이 사태는 막혔습니다. ownership만 명확했다면 oxios는 ProviderCircuitBreaker 위에 안 얹고 자체 도메인 구현만 했을 것이고, 거버넌스만 있었다면 oxios가 opt-in 표지를 미리 보고 정책 결정을 했을 것입니다.

따라서 이 문서의 요청은 두 축을 동시에 다룹니다. 거버넌스(R1·R2·R3·R7)는 owner가 변할 때의 안전망이고, ownership(R0·R5·R6)은 owner를 처음에 명확히 하는 첫 단계입니다.

4. 구체적 요청 항목 (R0–R8)

R0 · [P0] Ownership Contract — 누가 무엇을 소유하는지 명시

P0.2 사태의 구조적 근본 원인입니다. 이걸 못 박기 전엔 R1–R3(거버넌스)도 무의미합니다.

요청: docs/oxi-sdk-ownership.md에 다음을 명시적으로 기술:

SDK가 소유 (구현 제공 + 안정성 보장)SDK가 의도적으로 안 함 (consumer 책임, SDK는 trait/composable 인터페이스만 제공)
  • 에이전트 루프 (Agent::run_streaming)
  • 프로바이더 transport (Anthropic, OpenAI, …)
  • Tool calling 프로토콜
  • 기본 재시도 (3회, 지수 백오프)
  • Credential store
  • Catalog (models.dev sync)
  • Token usage tracking
  • MCP 프로토콜 (전송·메시지 형식) — SDK 소유
  • 메모리 포트 trait (MemoryStore) — SDK 소유
  • 회로차단기 behavior trait (CircuitBreaker) — SDK 소유
  • 도메인-특화 도구 (브라우저, 캘린더, …)
  • 채널 (Web, CLI, Telegram)
  • 프로세스 스케줄링, 작업 큐
  • A2A / inter-agent 메시징 프로토콜
  • 지식 베이스 (markdown/vector)
  • RBAC / path sandbox
  • 메모리 압축 (Snapcompact)
  • UI (TUI / Web)
  • MCP spawn validation 정책 — consumer 책임
  • 메모리 tiering 정책 (Hot/Warm/Cold) — consumer 책임
  • A2A / 도메인 트래픽 임계값 — consumer 책임

왜 두 컬럼? SDK가 동작 인터페이스(behavior)는 소유하고, 정책(policy)은 consumer에 위임하면 양쪽이 평행 진화하지 않습니다. 예:

  • SDK: pub trait CircuitBreaker { fn check(&self); fn record_success(&self); fn record_failure(&self); } + reference 구현.
  • Consumer: 자기 도메인 트래픽 (A2A / LLM / HTTP)에 맞춰 임계값 결정, SDK trait impl만 작성.
  • SDK가 reference 구현을 변경해도 consumer는 trait impl만 안정성 보장.

검증: oxios가 자체 A2ACircuitBreaker를 oxi_sdk::CircuitBreaker trait impl로 표현할 수 있고, oxi-sdk가 DefaultCircuitBreaker를 옵션으로 제공하면서도 oxios 도메인 정책은 보존되는 구조.

R1 · CHANGELOG의 `Removed` / `Breaking` 섹션 의무화

요청: 0.56 → 0.63 사이 166개 섹션 중 ## Removed 또는 ## Breaking로 분류된 항목이 0개였습니다. 2730 LOC의 multi_provider / complexity_router / provider_pool와 2061 LOC의 circuit_breaker / fallback_chain 삭제는 단 한 줄의 ## Breaking 항목도 없이 일어났습니다.

기대 동작: 0.x 시맨버이므로 breaking change가 허용되더라도, 제거/시그니처 변경/의미 변경은 ## Removed 섹션에 다음을 포함:

  • 심볼명 (full path: oxi_sdk::ProviderPool)
  • 대체 API 또는 마이그레이션 경로
  • 최소 deprecation 윈도우 (제거 N 릴리스 전)
  • 영향을 받는 알려진 consumer (GitHub 코드 검색으로 자동 산출 가능)
R2 · 공개 심볼 제거 전 `#[deprecated]` 주기 의무화

요청: 0.63의 oxi-sdk/src 전체에서 #[deprecated] 어노테이션이 0건입니다. oxios가 사용하던 4개 심볼은 사전 경고 없이 제거됐습니다.

기대 동작:

  • 제거 후보가 된 공개 심볼은 최소 1개 릴리스 (이상적으로 2개) 동안 #[deprecated(since = "0.XX.0", note = "use X instead; will be removed in 0.YY.0")] 마킹.
  • cargo build 시 consumer가 경고를 받게 함 → 마이그레이션 작업의 기계 판독 가능한 신호.
  • deprecation과 removal 사이에 API 시그니처 변경은 금지 (의미적 안정성 유지).
R3 · Stability Tier 어노테이션 (opt-in 표지 기계 판독화)

요청: oxi-sdk의 모든 pub API에 다음 tier 어노테이션 중 하나 부여:

#[stable(since = "0.XX.0")]            // semver-stable, 1 minor 동안 deprecation 없이 제거 금지
#[unstable(feature = "...")]          // 언제든 변경 가능, consumer는 명시적 opt-in
#[deprecated(since = "...", note = "...")]
#[internal]                            // pub이지만 consumer 대상 아님, 문서화/모듈 path 통제

근거: ae441c1f 커밋 메시지는 ProviderPool을 "opt-in multi-provider routing layer"라고 부르지만, "opt-in"은 oxios가 자동으로 감지할 수 있는 표식이 아닙니다. tier 어노테이션이 있었다면 oxios는 #[unstable] 위에 핵심 회복력을 얹지 않았을 것입니다.

기대 동작:

  • cargo doc에서 tier별 색상 구분.
  • #![warn(deprecated)] + #![warn(unstable_used)] 같은 lint 토글이 consumer 측에서 강제 가능하도록.
  • SemVer 정책 문서(docs/release-process.md)에 tier별 변경 규칙 명시.
R4 · SDK 내부 zero-panic 보장 + `Result` 일관화

요청: oxi-sdk/oxi-ai/oxi-agent 내부의 .expect(), panic!(), unreachable!()를 에러가 회복 가능한 모든 경로에서 제거. 0.59의 F-3 수정(14개 .expect() → ?)이 그 방향의 첫걸음이었습니다.

현재 상태:

// Before 0.59 (실제 있던 코드)
let headers = HeaderMap::try_from(value)
    .expect("valid header value");  // malformed API key → panic → panic=abort 데몬 사망

// 0.59+ (수정 후)
let headers = HeaderMap::try_from(value)
    .map_err(ProviderError::InvalidResponse)?;  // SDK가 Result로 변환

기대 동작:

  • 공개 에러 타입을 thiserror-based 단일 enum (SdkError)으로 통합하고 #[non_exhaustive]로 표시.
  • SDK 내부 코드베이스에 deny(clippy::expect_used, clippy::panic, clippy::unwrap_used) 같은 lint 적용 (테스트 코드 제외).
  • 0.59의 F-3처럼 각 프로바이더 transport에 동일한 변환 적용 (Anthropic, OpenAI, Azure, Mistral, Bedrock, Vertex, Google).
R5 · SDK Ownership Manifest (R0의 공개 문서화)

요청: R0의 ownership contract를 docs/oxi-sdk-ownership.md 또는 oxi-sdk/README.md에 명시적으로 문서화. 위 R0 테이블 그대로.

왜 R0와 별개인가: R0는 ownership 정의 자체, R5는 그것을 consumer가 발견 가능한 위치(README·docs 사이트)에 배치하는 운영 항목. R0만으로 oxios가 기여 시점에 합의한다면 좋고, R5는 그 합의가 영구히 노출되도록 보장.

R6 · Composable Trait 노출로 평행 진화 방지

현재 패턴: SDK가 ProviderCircuitBreaker를 직접 구현해서 consumer가 그것을 사용. SDK가 MemoryBackend를 trait으로 노출하지만 이미 MemoryStore trait이 있어서 이중화.

이상 패턴:

// SDK가 behavior trait만 노출 (R0에서 owner로 선언)
pub trait CircuitBreaker: Send + Sync {
    fn check(&self) -> Result<(), BreakerError>;
    fn record_success(&self);
    fn record_failure(&self);
}

// SDK가 default 구현도 제공 (opt-in, reference)
pub struct DefaultCircuitBreaker { /* 기존 impl */ }
impl CircuitBreaker for DefaultCircuitBreaker { ... }

// Consumer는 자체 구현 가능 (도메인 정책)
impl CircuitBreaker for MyDomainBreaker { ... }

// 그리고 SDK가 "reference composition"으로 wire
pub trait AgentResilience: Send + Sync {
    fn breaker(&self) -> &dyn CircuitBreaker;
    fn retry_policy(&self) -> RetryPolicy;
}

기대 효과: oxios가 자체 A2ACircuitBreaker를 동일한 trait으로 wire할 수 있고, SDK가 제공한 default 구현을 domain-specific 구현으로 교체 가능. 기능을 잃지 않으면서도 consumer 도메인을 존중 — 평행 진화가 일어나지 않음.

R7 · 공개 에러 타입에 `#[non_exhaustive]` + named variant 안정성 보장

요청: oxios는 oxi_sdk::ToolError를 34회 매칭합니다. SdkError, ProviderError 등도 다수. 공개 에러 타입에 다음 보장:

  • #[non_exhaustive] 어노테이션 — 새 variant 추가는 자유롭게 허용 (consumer는 catch-all 필요).
  • 단, 기존 named variant의 의미는 변경 불가 — variant 이름이 같아도 의미가 바뀌면 사실상 silent break.
  • 의미 변경 시 RenameVariant 같은 명시적 신호 + deprecation.
  • 이 규칙을 docs/release-process.md에 명문화.
R8 · 신규 transitive 의존성 영향 명시 + feature 분리

요청: 0.63이 prost + vendored protoc-bin-vendored를 새로 끌고 온 것은 oxios의 빌드 시간을 비약적으로 증가시킵니다. 컨테이너/edge 빌드에서 큰 부담입니다.

기대 동작:

  • 신규 transitive 의존성 추가 시 CHANGELOG에 빌드 영향 (예: +~120 crates, +~150s cold build time) 명시.
  • 큰 빌드 의존성(protoc, lalrpop, tonic, protobuf 등)은 feature gate 뒤로 분리. 예: oxi-sdk/proto-catalog = ["oxi-catalog"].
  • consumer가 정말 필요로 하는 기능이 아닌 한, default feature에 heavy build dep을 포함시키지 않기.

5. 현재 vs 이상 구조 delta

현재 (oxi-sdk 0.63)

  • Ownership: 불명 (코드와 README 어느 쪽에도 "누가 무엇을 갖는지" 없음)
  • oxios가 자체 MCP / 메모리 / 회로차단기 구현 (평행 진화)
  • pub use 80줄, root-level re-export 50여 개
  • #[deprecated] 0건
  • stability tier 어노테이션 0건
  • CHANGELOG의 ## Removed / ## Breaking 분류 0건 (0.56–0.63)
  • SDK 내부 zero-panic 미보장 (F-3 수정 0.59에서 시작)
  • 에러 타입 일부 #[non_exhaustive] 적용
  • 신규 build dep (prost, protoc-bin-vendored) default에 포함

이상 (제안)

  • Ownership: README + docs/oxi-sdk-ownership.md에 behavior ↔ policy 분류 명시
  • SDK가 behavior trait + reference 구현, consumer가 policy impl
  • pub use 동일 + 각 라인에 stability tier 명시
  • 제거 후보는 최소 1~2 릴리스 #[deprecated] 경고
  • #[stable] / #[unstable] / #[internal] tier 어노테이션
  • CHANGELOG ## Removed 섹션 의무, 대체 API 명시
  • SDK 내부 deny(clippy::expect_used, panic, unwrap_used)
  • 모든 공개 에러 타입 #[non_exhaustive] + 의미 변경 금지 정책
  • heavy build dep는 feature gate, default는 경량

6. 기여 형태 제안

oxios는 fork를 만들거나 자체 패치를 유지하기보다는, 다음 중 하나를 선호합니다 (우선순위 순):

  1. R0 (ownership contract) + R5 (manifest) 공동 작성: 가장 임팩트가 큰 변경. oxios가 1차 초안 작성 → oxi 측과 합의. 양 측 도메인 전문가 1~2명이 합의하면 영구 해결.
  2. R6 (composable trait) PR: CircuitBreaker / MemoryStore / McpTransport를 trait + reference 구현으로 리팩터링. 호환성 유지하면서 단계적 도입 가능.
  3. R1·R2 (CHANGELOG + #[deprecated]) PR: governance 개선. 도메인 중립이라 upstream 흡수가 가장 자연스러움.
  4. R3 (tier 어노테이션) PR: 어노테이션 추가만이라 위험 0. 거버넌스 작업의 첫 걸음으로 적합.
  5. R4 (zero-panic) PR: F-3 작업의 후속. 프로바이더별로 분할 가능 (단일 PR 부담 적음).
  6. R7·R8 문서화: docs/release-process.md 업데이트 + feature 분리 제안.

oxios의 시간/자원 한계상, 1번(R0+R5)이 구조적으로 가장 가치 있고, 3번(R1·R2)이 가장 빠르게 흡수 가능합니다. 1번 합의 시 3~6번의 작업은 자연스럽게 따라옵니다.
