0. 두 질문에 대한 직접 답변

Q1. oxi-sdk가 잘못된 거야?

공유 책임입니다. 어느 한 쪽이 일방적으로 잘못했다고 보지 않습니다.

  • Rust 0.x 시맨버는 0.x→0.x에서 breaking change를 허용합니다. 기술적으로 oxi-sdk는 자기 카르타를 지킨 것이고, "잘못"이 아닙니다.
  • 단, governance 갭은 분명히 존재합니다. P0.2/P0.2b 리팩터링은 4개 공개 심볼(ProviderPool, RateLimitPolicy, ProviderCircuitBreaker, CircuitBreakerConfig)을 삭제했지만, 0.56–0.63 사이 어느 CHANGELOG 엔트리에도 이 삭제가 언급돼 있지 않습니다. 의도적 opt-in 정리라도 마이그레이션 경고는 사용자의 책임이 아니라 판매자의 책임입니다.
  • 반면, oxios 측의 결합 위험도 사실입니다. oxi의 커밋 메시지는 ProviderPool을 "opt-in multi-provider routing layer"라고 명시적으로 부르고 있었고, oxios는 그 위에 핵심 회복력 기능(provider pooling + LLM circuit breaker)을 올렸습니다. "opt-in API 위에 핵심 기능을 얹는 것은 위험하다"는 교훈은 oxios가 가져가야 할 몫입니다.

결론: oxi는 governance를 개선해야 하고, oxios는 opt-in API 위에 회복력을 쌓는 설계를 재검토해야 합니다.

Q2. 업그레이드 하는 게 더 좋다는 거야?

네, 그러나 점진적으로 — 그리고 첫 단계는 무료입니다.

이 결론은 한 가지 팩트에 매달려 있습니다: 제거 커밋이 처음 포함되는 릴리스가 v0.61.0입니다 (git tag --contains ae441c1f | head -1로 검증). 즉:

  • 제거가 0.61.0에 랜딩했다면 → 0.59.0은 무손상 도약이 가능하고, 거기서 멈추는 게 최적입니다. F-3(데몬 panic-safety), F-10(SSE 청크 누락 수정), F-1(자격증명 마스킹)을 무손상으로 얻습니다.
  • 제거가 0.59.0에 이미 랜딩했다면 → 무료 중간지대가 없으므로 "reimplement vs stay"만 남습니다.

현실은 전자입니다. 그래서 1차 액션은 명확합니다: oxi-sdk = "0.59.0" 도약. 이후 0.61의 additive 기능(Snapcompact, PortMemoryBackend, Codex/Gemini 디스패치)은 별도 평가 후 단계적으로.

2. 왜 0.59.0이 안전한가 (제거의 의도)

ae441c1f 커밋 메시지:

"Delete the complexity-routing machinery that was never constructed in production (only doc comments and self-tests referenced it)"

afe9cf04 커밋 메시지:

"The agent loop's retry logic (stream_retry.rs: 3 attempts, exponential backoff, retryable-error classification) is fully independent of the circuit breaker. The CB only added a pre-stream gate that could block requests after transient failures — removing it simplifies the retry path without losing any resilience."

핵심 통찰

  • Provider 풀링: oxi 측에서도 프로덕션 사용 0. oxios는 provider_rpm == 0이 기본값이므로 비활성 경로.
  • LLM 회로차단기: oxi의 에이전트 루프가 이미 자체 재시도(3회, 지수 백오프)를 갖고 있어 중복 안전장치. 삭제해도 회복력 손실 없음.

따라서 0.61 이후로 강제 마이그레이션을 감수할 구조적 이유가 없다 — 핵심 회복력은 oxi 에이전트 루프에 내장돼 있고, oxios는 자체 A2ACircuitBreaker(crates/oxios-kernel/src/a2a/circuit_breaker.rs)로 A2A 경로를 보호하고 있음.

6. 검증된 안전 지점 (코드 직접 확인)

CHANGELOG 분석만으론 보이지 않는, 코드를 직접 읽어 확인한 사실:

  • AgentConfig { ... } 리터럴이 ..Default::default()로 끝남 (agent_runtime.rs:1006) → 새 필드 추가돼도 안전.
  • AgentEvent match에 _ => {} 캐치올 존재 (agent_runtime.rs:1519) → 새 이벤트 변형 안전. oxios는 이미 0.58의 ThinkingEnd / ToolCallDelta를 명시 처리 중.
  • CompactionStrategy::Snapcompact(0.61 신규) → oxios는 Threshold(0.8)만 생성하고 enum을 match하지 않음 → 비파괴.
  • oxios-mcp는 oxi-sdk와 완전히 독립(stdio JSON-RPC 클라이언트 자체 구현) → 0.59의 MCP consent 게이트 무관.
  • oxibrowser-core ^0.17 vs oxios의 native-browser 피처 → 버전 충돌 없음 (cargo update 깔끔).

8. 종합 의견 — 다시 한 번

"oxi-sdk가 잘못된 거야, 우리가 변경해야 하는 거야, 업그레이드가 더 좋다는 거야?"
  • 잘못의 분담: oxi-sdk의 governance 갭(CHANGELOG 미기재) + oxios의 opt-in API 위 결합. 어느 한 쪽 탓이 아닙니다.
  • 변경의 필요: 0.59.0까지는 없습니다 — 무료 도약 가능. 0.61.0부터는 옵션 (reimplement / drop / stay).
  • 업그레이드 권장: 예 옵션 A(0.59.0)부터 시작하세요. F-3(데몬 panic-safety)과 F-10(SSE 청크 누락 방지)은 oxios의 핵심 안정성 이슈다운데, 비용은 두 줄 변경과 lock 업데이트뿐입니다. 이후 0.61의 additive 기능은 실험적으로 평가.
